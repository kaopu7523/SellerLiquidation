# 亚马逊 FBA 尾货攻略站 + 免费库存发布栏目 — SPEC

状态：已通过 brainstorming 评审，待用户最终确认
最后更新：2026-08-28

## Problem Statement（问题陈述）

亚马逊 FBA 中小卖家在库存滞销时面临双重困境：一是不知道怎么处理（移除费/仓储费如何计算最划算、如何合规低价甩卖、税务物流注意事项不清楚）；二是不知道卖给谁（缺少一个集中、公开的展示渠道，只能靠零散的人脉和微信群/Facebook 群等私域渠道撮合）。目前市面上没有一个专门聚焦这一细分场景、内容+发布渠道一体化的网站。

## Proposed Solution（方案描述）

建立一个以 SEO 内容为主导的网站：

**内容矩阵**：借鉴游戏攻略站方法论，先挖掘长尾关键词，再据此规划内容页面，主轴覆盖 ①FBA 仓储/移除费规则解读 ②清库存实操攻略（定价、找渠道、线下对接、税务物流）

每篇攻略文章末尾固定放置一个发布入口 CTA（如"免费发布清库存信息，马上清空滞销库存"），点击直接跳转到发布表单，作为"内容→发布转化"闭环的具体落地点

**免费发布栏目**：卖家注册账号后（邮箱为主，微信为可选辅助方式，无需人工审核）即可免费发布滞销库存信息，**每位卖家每日最多发布 3 条**，字段包括：

- 产品图片
- 产品名称
- 产品链接
- 下架原因（如需要下架）
- 平台售价
- 产品描述
- 数量
- 入仓日期
- FBA/海外仓（多选，可同时勾选两者，因为同一批库存可能同时分布在 FBA 和海外仓。勾选 FBA 需填写具体仓库代码，勾选海外仓需填写具体地址；均为自由文本，不做格式校验，方便买家判断物流/提货可行性）
- 采购成本（Cost Price，不预设卖家采购来源地）
- 意向抛货价
- **联系方式**（自由文本，卖家自行填写微信/邮箱/电话等一种或多种；提交前展示风险提示："联系方式将公开展示，可能被骚扰或爬取，请自行判断填写哪种"）

以时间顺序展示墙形式呈现。每条库存信息系统自动记录并展示"发布时间（Published）"和"最后更新时间（Updated）"，不需要卖家手动填写。卖家可在"我的发布"页对自己的库存点击"刷新/库存还在"按钮，将最后更新时间刷新为当前时间，让买家判断这条信息是否还有效——**限制每条信息每天最多刷新一次**，且刷新只更新时间戳数字，**不改变该条信息在展示墙上的排列位置**（避免变成"顶帖"竞争，展示墙仍严格按发布时间顺序排列）。

卖家可自行标记"已成交/已下架"，标记后的信息**保留在墙上并以灰显样式呈现**（不直接移除）——用于形成社会证明，弥补平台不做支付/担保导致缺乏 GMV 等活跃度指标的问题。

**买家侧**：不限定画像，任何有意向的买家均可浏览，但需要注册账号（邮箱验证或 Google 登录）后才能查看发布墙及库存详情。攻略内容页面本身**保持完全公开、无需登录**（这是 SEO 自然流量的入口，不能被登录墙挡住），登录门槛只加在发布墙/库存详情这一层。

**闭环逻辑**：内容吸引卖家自然搜索访问 → 卖家在解决"怎么处理"疑问的同时被引导去发布库存 → 库存信息本身也可能反过来带来更多流量和口碑

## Positioning（定位与语言策略）

- 目标用户是**全球 FBA 卖家**，不局限于中国卖家，不做成"中国内销风格"网站
- **MVP 阶段内容语言：英文单轨**，走 Google SEO 体系
  - 理由：双语内容会让关键词研究、内容生产工作量翻倍，拖慢核心闭环（内容→发布转化）的验证速度；英文内容覆盖面更广，也更契合"不做中国内销站"的定位
  - 中文内容作为**后续可能的扩展**，待核心闭环验证成立后再评估是否加入，不在本期 MVP 范围内
- 注册方式：**邮箱（需邮箱验证）为主，支持 Google 登录**，微信作为可选辅助登录方式保留（照顾华人卖家），不作为默认/主要方式
- 所有用户（含仅浏览的买家）均需注册后才能访问发布墙/库存详情，用邮箱验证 + 每日发布频率限制（3 条/天）共同构成 MVP 阶段的轻量反滥用机制

## Technical Constraints（技术约束）

- 前端框架：Next.js + React
- 开发方式：使用 Claude Code 辅助开发
- 数据库与用户认证：使用 BaaS 服务（Supabase/Firebase），自带数据库+认证体系
- 图片存储：使用同一套 BaaS 服务自带的存储
- 违禁内容防控：发布时关键词自动过滤 + 用户举报机制（事后下架），无人工预审
  - 关键词过滤词库：MVP 阶段采用现成的英文违禁/敏感词开源词库起步，后续根据举报反馈迭代补充（具体选型留待技术架构阶段确定）
- **举报处理流程**：举报触发后，系统邮件通知运营方（创始人/小团队），由人工手动核实并决定是否下架。不做基于举报次数的自动阈值下架（防止被恶意刷举报滥用，比如竞对互相举报对方信息）
- **用户协议/免责条款**：MVP 阶段即上线。注册/发布流程需勾选"我已阅读并同意《用户协议》"，协议内容需明确"发布内容真实性由发布者自行负责，平台不担保交易结果、不介入买卖双方纠纷"等条款

## Non-goals（明确不做的事）

- 不做在线支付/担保交易（买卖双方线下自行谈价、打款、交割）
- 不做站内即时通讯（联系方式走微信/邮箱等站外渠道公开展示，不做转发中间层，不做点击查看等防爬虫机制——MVP 阶段优先"清库存速度"，联系方式暴露风险由发布者自行判断承担）
- 不做移动端原生 App（只做响应式网页）
- 不做发布信息的筛选/搜索功能（MVP 阶段仅展示墙）
- 不做付费订阅/查看联系方式收费（暂不以此变现；用户规模起来后"付费查看联系方式"是潜在的商业化方向，待后续单独评估，不影响当前 MVP 设计）
- 不做预防性选品避坑类内容（内容聚焦"已滞销怎么办"，不做"如何避免滞销"）
- 不做人工审核发布内容（仅靠关键词过滤+举报机制兜底）
- MVP 阶段不做中文内容（见 Positioning 一节）
- 不做冷启动人工填充库存信息（发布栏目依赖纯自然增长，不自己或找人先发示例库存）

## Success Criteria（成功标准）

采用组合指标验证 MVP 是否值得继续投入：

- **发布量**：一定周期内，有真实卖家主动发布滞销库存信息，达到有意义的数量
- **内容流量**：攻略内容通过 SEO 带来自然搜索访问量，验证长尾词打法是否跑通
- **转化率**：内容访问者中，有一部分最终转化为发布库存的卖家，验证"内容引流→带动发布"这条核心链路是否成立

## Open Items for Technical Architecture Phase（留待技术架构阶段细化，非阻塞）

- 违禁词库具体选型与维护方式
- 数据库表结构、图片存储的格式/大小限制
